# Build a Proof Atlas

Bind the requested edition first. Compare the title, version, TeX and PDF. Record the source revision and SHA-256 digests. If an unversioned URL and a local checkout disagree, check the version-specific record and submission archive. Distinguish a local PDF from the PDF served by a publisher.

Record the edition's canonical HTTP(S) URL in `project.json` as `publication` and its human-readable citation in `edition`. Each build links that citation and the exact bundled manuscript PDF in the explorer and dashboard headers. When hosting is configured or moved, refresh the paper repository's renderer snapshot (or pinned release), rebuild, and verify both header links from the deployed explorer and dashboard. The PDF link resolves under the site's own base path. For an unpublished manuscript, leave the citation as text and keep the PDF link active.

## Author review and orientation

On the first build, open the explorer and dashboard and give their full URLs or absolute paths, the current claim, the authorized stopping point, and the phrase “Open the local review dashboard for this paper.” Point readers to **How to use this atlas**. Start or reuse the local review server whenever requested, including during proof work or on a later day.

Read new review feedback at checkpoints and on resume. For every paper claim, run the [independent correspondence workflow](references/correspondence.md) at statement preparation and again on checked evidence. Automatically write the author-facing analysis when each claim is checked and backfill missing analyses when resuming an older atlas. Show why the cases agree or differ, identify the scope, and recommend approval, a specific correction, or a clarification. Resolve discrepancies and continue the authorized scope. The dashboard reports formal checks, optional author review, outstanding differences and the next actor separately. A known mismatch reopens the paper obligation while preserving evidence for the actual formal result. Human review is optional and never gates an otherwise completed proof run. Only a human records author decisions. For review, migration or publication use the [author guide](references/author-guide.md).

### Carry review findings through to delivery

When reviewing or resuming, run `python <skill>/scripts/atlas.py review-work PROJECT`. Do this again after feedback, at checkpoints and before handing back control. Act on proof-agent tasks within the existing authorization during the same session. A review request can uncover a repair covered by an earlier paper-wide or single-claim authorization. Carry it out without asking the reviewer to file the finding again. Respect requests for assessment only and any explicit pause. The owner field assigns responsibility; report a check as running only when a real process or workflow is running.

A successful scratch proof is an intermediate result. Integrate it into the tracked Lean package, connect the paper claim to the declaration that includes the fix, refresh its audit and affected dependent audits, and repeat the correspondence comparison. Record the resolution against the original feedback IDs. For authorized hosting, commit and push the scoped repair, wait for enabled CI and Pages, then open the deployed claim and compare its evidence with that commit. Keep local-only projects local. The author alone can approve correspondence or decide a genuine change in the intended mathematics.

Before declaring completion run `atlas.py review-work PROJECT [CLAIM ...] --check` for the authorized scope. For a GitHub-verified release add `--require-ci --ci-receipt PATH` using the downloaded receipt for the published commit. Check the live page separately. Continue on open agent work or missing evidence. If blocked, record the issue, owner, last verified stage and concrete next action and tell the author what remains. Name any actual author questions separately from optional approvals. A stopped session saves the queue for resumption; the static website cannot launch a coding agent.

## Start a project

Introduce the paper on the homepage when building the first atlas. Record the full author list in manuscript order in `project.json` under `authors`. Verify the title, edition-specific citation and link, and supply the publication year or verified version date in `citation_details`. For arXiv, use the versioned identifier. Write a short `paper_overview` describing the paper’s question and distinguish any conjecture from established results. The shared homepage explains the Plain English, Paper, Lamport proof and Lean views, the direction and coverage of dependency arrows, and how to use the dashboard and verification evidence. Check the homepage and its navigation after publication. Cached imports can supply each author with a separate `--author` and the date with `--citation-details`.

Use the bundled **Folio** renderer for new and resumed atlases. Its overview pairs a featured result with a manuscript figure above a compact contents list. Keep the full citation and reading guide in the masthead disclosure. The reader, graph and dashboard share the same typography and navigation. Preserve incoming claim/view links and each claim's actual verification state.

In `project.json`, the optional `folio` object accepts `short_title`, `featured_claim` (a manuscript label), and an optional short `blurb`. Choose a representative result independently of the active proof target. When the manuscript has a useful figure, save a legible raster crop in the paper repository. Set `folio.figure` with its project-relative `path`, descriptive `alt`, `caption` including its manuscript figure number, and one-based PDF `page`. Inspect the crop against the bound edition. Without a figure the lead reflows as text, and without configuration the first inventoried claim is featured. When publishing a redesign, rebuild with the refreshed renderer and check the contents count, all four reading views, whole-paper graph, dashboard and evidence links at desktop and phone widths.

For arXiv, run `python <skill>/scripts/import_arxiv.py <arxiv-url> <new-project>`. It resolves the edition, downloads and hashes the source and PDF, follows literal TeX inputs, inventories labeled claims, and builds both views. A cached edition can be imported using its versioned ID, `--title`, `--archive` and `--pdf`. If multiple main files exist, select one with `--main`. On resume, open the existing project instead of importing again.

Read `import-review.json`. The importer matches unique named headings to PDF pages when pdftotext or PyMuPDF is available. Verify those matches and fill unmatched pages. Review proof citations and equations in context before adding justified edges to `reader.json`; citations in adjacent proofs are only candidates. Reconcile custom environments, unlabeled claims, detached proofs, macro-based includes, and any unvisited sources. The first generated reader is an inventory for further work.

Check `python <skill>/scripts/hosting.py <project>` on first import and resume. A pending decision calls for a user-facing question, including during tests on a real paper. Continue local builds while waiting. Once the author replies, record the answer with `--local` or `--github OWNER/REPO --visibility public --pages` (use the chosen visibility and Pages option). Local-only requires an explicit choice. When GitHub publication is authorized, stage the selected files and workflow, review and commit them on main, then run `hosting.py <project> --publish`. Follow the triggered deployment to completion and verify the live URLs.

**Ask where the author wants to host this paper's Proof Atlas.** At first setup, propose a specific repository based on the paper slug and any organization the author already named. Ask only for unresolved choices: owner/repository, visibility, and whether to publish the reader and dashboard as a website. Offer local-only when hosting has not been requested. Accept a custom destination or an existing repository. Continue the local import and preview while waiting. Reuse a previously chosen destination on resume. Keep the reusable skill independently distributable.

During parallel proof work, publish a reviewed commit while other authors continue in the same checkout. Include each newly checked source, its transitive local dependencies, and the evidence referenced by the inventory. The publishing helper compares recorded input hashes with the committed Git blobs and pushes that revision. Reconcile reported mismatches, then verify the deployed claim rows and downloadable audits against the local receipts.

When GitHub hosting is chosen, ask once whether GitHub Actions should independently rebuild the Lean proofs and publish per-claim verification links. Honor an existing choice. Record approval with `hosting.py <project> --lean-ci` or a decline with `--no-lean-ci`. For an enabled project, the agent installs the [Lean workflow](references/verify-lean.yml), includes the current scripts, assets and references/author-guide.md at `tools/proof-atlas`, and integrates the verification-artifact step and completion trigger from the [Pages workflow](references/github-pages.yml). Reuse compatible existing CI and preserve custom deployment steps. Trigger the check, monitor it, and verify the published badges. If Actions or a pinned dependency is unavailable, keep the local evidence visible and report the blocker.

The explorer and dashboard show **Lean checked** for an audited paper claim, **Subproofs checked** for checked parts of an unfinished claim, and **Machine verified on GitHub** only when the trusted workflow independently checked that declaration and expected type at the published commit. Changed inputs require a fresh check. The Plain English and Lamport proof views carry the label "Explanation, not machine-checked", and the homepage explains what each badge does and does not mean. Never describe those views as verified. The audit assumes proof files written in good faith: the type and axiom checks catch an honest agent's mistakes, not a proof built to game them. When the author needs protection against untrusted proof files, recommend a dedicated checker such as the Lean FRO's Comparator.

**Publish and verify the evidence readers can click.** Show a prominent ✓ Machine verified on GitHub badge on each verified dashboard row, in the explorer's claim list, and above the reading tabs when a reader opens that claim. Link the header and dashboard badges to the exact successful run attempt. Place direct links to the original GitHub Actions artifact and a publicly readable verification record beside those badges. When a reader selects the GitHub artifact, explain the sign-in requirement and offer the public verification record alongside the download. After Pages deploys, open a claim in its default reading view, follow the links, and compare the published record with the downloaded artifact. Check every badged declaration, expected type, audit digest, and commit against that run. Report the live explorer and run URLs once these checks pass.

Once the author selects hosting, the agent provisions or connects the repository and pushes the paper-specific project. Include the manuscript inputs, editable claim and dependency data, Lean sources and lockfile, selected build evidence, and reproducible renderer tooling or a pinned renderer release. Exclude installed toolchains, dependency caches, and unrelated workspace files. Use project-relative paths and review the outbound file list. When Pages is selected, configure the deployment, wait for the published build, and test the explorer, a deep-linked claim and graph, dashboard, PDF and evidence under the repository subpath. Report the repository and verified site URLs. For GitHub Pages with a renderer snapshot at `tools/proof-atlas`, adapt [the Pages workflow](references/github-pages.yml). Save the destination in project.json under `hosting`, separately from the manuscript's source repository.

Place project data in the author's chosen output directory. Keep this skill directory portable. The current helper reads explicitly listed UTF-8 source files in manuscript order. Follow TeX includes yourself and supply each file. Inspect the inventory for custom macros, unlabeled claims, assumptions in prose and detached proofs. Reconcile these before claiming complete coverage.

Create a UTF-8 `project.json` with `schema_version` set to 1, `title`, `edition`, `revision`, `tex` (ordered array of records with `path` and `sha256`), `pdf` (same record shape), and `environments` (array of theorem environment names). Paths are relative to the project. Optional `focus` is a TeX label. Optional `work` contains per-label checkpoints as described below.

**Launch both views on first import.** As soon as the initial project and source inventory are available, the agent runs `python <skill>/scripts/preview.py <project-directory> --open` and keeps the local preview running during formalization. This performs the first build before serving or opening anything. In a headless host omit `--open` and report the two printed URLs. If desktop launch is provided separately by the host, open both URLs there. Reuse an existing preview for the same project. Include the full absolute HTML paths when reporting local files.

The preview produces the reader at `dist/proofs/index.html` and the separate dashboard at `dist/progress.html`. A new project immediately has a searchable inventory, four reading views, and an initially empty dependency map. Missing proof material is shown as pending. As the agent saves project records, companion text, selected Lean sources or evidence, the preview rebuilds both pages and open HTTP tabs reload at the same claim and view. Checkpoint after each meaningful proof attempt or discovery. For CI or a static snapshot, run `python <skill>/scripts/atlas.py build <project-directory>`; the same command generates both entry points. Direct file opens show the last snapshot.

**Populate the public explorer.** Optional `reader` in project.json points to a UTF-8 JSON object with `schema_version: 1`, a `claims` mapping keyed by label, and a `dependencies` list. Claim metadata can include a printed `reference`, checked PDF `page`, `summary`, `sketch`, project-relative `lamport` Markdown file, `origin`, and `source_url`. Preserve existing structured proofs and their provenance. Edges contain `claim`, `prerequisite`, and `reason`. Identify the covered mathematical step when a claim has several conclusions. Record only substantiated edges. The Whole paper graph includes every inventory claim, including conjectures and claims without recorded links. Check that its node count stays constant across selections and that Selected chain follows only the selected claim, its prerequisites and its dependents. Test a claim, graph neighbor, all four reading views, the exact PDF page and a verification log through the actual preview. On first use, also demonstrate that an open dashboard and reader reflect a saved checkpoint.

## Work on a claim

**Record the author's stopping condition before starting or resuming formalization.** Read the author's instructions and existing `project.json`. If the author requests all results, set `proof_work` to `{"mode":"paper"}`. If they request one claim, set it to `{"mode":"claim","claim":"<label>"}`. Ask which scope they want only when it is genuinely unresolved. A preview or review request alone does not authorize formalization. Keep the scope across sessions. Apply a later change immediately, record an explicit pause with `"paused":true`, and clear it when the author resumes.

Tell the author the scope, current claim and stopping condition in the interactive terminal at start, resume and scope changes. The dashboard's claim inventory displays the same saved authorization beside the actual activity. Report meaningful progress as the claim, subproof, latest Lean result and next authorized work. In paper-wide mode, after each checkpoint or closure immediately continue the next obligation or eligible claim. Use writing time between Lean runs to advance the mathematics. In single-claim mode, continue through its prerequisites and the final paper-level audit, then report closure and wait. If a blocker affects one branch, continue independent authorized work and retain the exact blocker. Stop only at the authorized boundary, an explicit pause or an impasse across the remaining authorized work.

For an executable evidence check, define the intended proposition in the statement directory (see **Separate statements from proofs**). Write a contract file outside that directory that imports the statement module and the proof module. Run `python <skill>/scripts/audit_lean.py <package> <contract.lean> <expected-proposition> <proof-declaration> --target <proof-module> --statements Statements [--witness <example>] --output <new-evidence.json>` after package setup. The helper builds offline, type-checks the declaration against the expected proposition, inspects its transitive axioms, and checks that the statement modules import no proof module and that the proposition is defined in one of them. With `--witness` it also checks the example described in **Show the hypotheses can hold**. For explicit module targets in supported packages, the receipt hashes the contract, the local sources imported transitively by the contract and targets, the package configuration, manifest and toolchain pin. The helper checks the dependency set and hashes again after Lean runs. A default build or unavailable dependency metadata uses full-package source hashes. Review the contract's correspondence with the paper and the pinned dependencies separately. Keep a partial result scoped to the checked subclaim.

**Separate statements from proofs.** The paper's statements and the definitions they use go in one directory of the Lean package, `Statements/`, declared in `lakefile.toml` as `[[lean_lib]] name = "Statements"`. Proofs go in other libraries, for example `Proofs/` with `[[lean_lib]] name = "Proofs"`. A statement module may import Mathlib and other statement modules, never a proof module. Lemmas that a definition needs may stay beside it. The expected proposition of each closure is a `Prop`-valued definition in `Statements/`, not in the contract file or a proof module. `audit_lean.py --statements Statements` enforces this, so a proof cannot change what it proves. When it rejects a layout, it names the statement file and the proof module it imports, or the file that defines the proposition. Move the definition into `Statements/` rather than relaxing the check. While proving, do not edit `Statements/` to make a proof go through. A change there is a change to the claim. Record why in the checkpoint and tell the author.

**Prefer Mathlib definitions and bridge custom ones.** Use upstream Mathlib structures and predicates in `Statements/` wherever practical. When domain ergonomics justify a custom definition, prove a short bridging or characterization lemma in `Statements/` connecting it to standard Mathlib primitives where one exists. The audit receipt records `noncomputable` flags and notation-free signatures (`pp.notation false`) for every local constant behind the statement, lists pinned external packages from `lake-manifest.json` (flagging any non-Mathlib third-party repositories), and reports the declaration's axiom profile (`Constructive (0 axioms)` vs. standard Lean/classical axioms). Surface any `noncomputable` gap against "explicit" or algorithmic claims and any third-party package in the comparison.

**Account for Lean's default values.** Lean makes every function total: x/0 = 0, log 0 = 0, `⊤.toReal = 0`, `sInf ∅ = 0`, ℕ subtraction stops at 0, singular matrices invert to 0, and `limUnder`, `tsum`, integrals, `condExp`, `deriv`, and `Function.invFun` return a default when the object does not exist. A statement built on one can be true and mean nothing. The audit lists each such use in the statement's definitions under `defaults` in the receipt (divisions by a nonzero numeral are omitted), and the Lean view shows the full scan. In each new comparison, save a short assessment keyed by each finding's ID under `analysis.default_assessments` (see the correspondence workflow). Mark it `justified` and name the supporting hypothesis, lemma, or intended convention, or mark it `needs attention` and state the missing fact. The review page puts open questions first and groups explained uses in a collapsed section. Open questions can remain when saving a comparison and preserve the Lean proof status.

`--statements` accepts a directory or a single file and may be repeated. An atlas audited before this check keeps building, and the build warns about each closure audited without `--statements`. To migrate one, run the audit with `--statements` naming the files that hold its statement and definitions, then move whatever definitions the audit reports into those files. Naming a file that mixes definitions and proofs also passes, but it makes those proofs part of the statement. Rerun the audit and update the closure with the new receipt.

An audit with `--statements` requires the standard package-root source layout and module paths the auditor can confirm with Lake. A custom library `srcDir`, for example, stops the audit with `Cannot verify statement independence`. Use the supported layout to obtain an independence receipt. Legacy audits can still record a full-package Lean check for custom layouts.

**Show the hypotheses can hold.** Contradictory hypotheses prove anything, and a guarded clause ("if f is differentiable at D, then …") is trivially true when the guard never holds. By default, try a concrete example or apply an existing lemma. If the example needs a new mathematical result, record its precise statement in the claim's `work[label].witness_missing_result` in `project.json`, then continue with independent claims. On resumption, reuse this note and revisit it when a relevant lemma becomes available or the author asks for more work. Ask the author only when their mathematical intent affects the choice of example or the reading of the statement.

Honor ordinary-language preferences without a setup question. Save a paper-wide instruction once as `witness_search` in `project.json`. The default is `available` when absent. “Skip witness searches for this paper” sets `skip`. “Pursue witnesses even when they need new lemmas” sets `pursue` within the agreed proof scope. For “Do the extra work for Theorem 8,” resolve the manuscript label and set only that claim's `work[label].witness_search` to `pursue`. Remove a claim override to inherit the paper preference again. `atlas.py review-work` reports the effective plan per claim. Preserve existing checked examples and pass their declarations to `--witness` again when re-auditing, including in `skip` mode.

When a witness is available, pass its declaration to the audit with `--witness`. Instantiate a non-degenerate case whenever the paper's regime is nontrivial (for example, a nonempty index set or graph, positive dimension or block length, or nonzero signal/channel) rather than satisfying universal binders purely via `Empty`, `∅`, or `0`. The audit derives the proposition the example must prove from the expected statement. Each binder of the statement's leading ∀/→ prefix becomes `∃ x` or a conjunct, and a ∀/→ inside the conclusion (a guarded clause, reached through ∧, ∃ and `let`) adds its binders too. A variable the theorem itself chooses under ∃ enters only when a guard mentions it. For example, `∀ n, 0 < n → n < 10 → …` needs `∃ n, 0 < n ∧ n < 10`. The example must prove exactly that proposition with only the standard axioms. On a mismatch the audit prints the proposition it needs. Put examples in their own library, for example `Examples/` with `[[lean_lib]] name = "Examples"`, importing only statement modules and Mathlib, and import that module from the contract. Write the statement's hypotheses as explicit ∀/→ binders. Only the expected definition itself is unfolded, and a conclusion written as `… → False` reads as a guard, so write `¬` instead. The receipt records the example, its source location and the derived proposition; the Lean view, review page and `review-inputs --side lean` show them; and GitHub verification rechecks the example. An audit without `--witness` passes with a warning, and the build labels such closures "No checked example shows the hypotheses can hold". Apply the same search preference to legacy closures. When a witness is checked, clear its outstanding missing-result note.

**Lock the statement before proving (Gate 1).** For every inventoried paper claim (its public `Statements/` target, not internal `Proofs/` helper lemmas), audit the statement **before** launching proof search. Write a statement contract importing the statement module (and optional `Examples/` module) and run `python <skill>/scripts/audit_lean.py <package> <statement-contract.lean> <expected-proposition> --statements Statements --statement-only [--witness <example>] --output <statement-audit.json>`. This verifies `Statements/` independence, fingerprints `statement.sha256`, scans `defaults`, and checks `--witness` if supplied, without building `Proofs/`. Attach `statement_check` (`{"audit", "package", "expected"}`) on the `drafted` checkpoint in `project.json`, then run `atlas.py review-inputs` and `atlas.py compare` per the [correspondence workflow](references/correspondence.md). Human approval is optional. If the comparison records `difference` or `unsure` with `actor: "Author"`, save the specific mathematical question in the review queue. In an interactive session show the paper passage and Lean statement side by side and ask, "Work through this now, or save it and continue with independent claims?" Honor the author's choice. If they choose to work through it now, pause proof search and help settle the interpretation. If they defer, or the session is unattended, hold the affected claim and any work that depends on the answer and continue with independent claims. Revisit deferred questions before the final summary and list any still open. As long as `Statements/` stays unchanged during proof search, `statement.sha256` matches at closure and the Gate 1 comparison and any author approval carry over automatically.

Start with a claim requested by the author, or one with a tractable prerequisite. Write the intended Lean statement and the definitions it uses in the statement directory before any proof. Record the hypotheses inherited from earlier passages, any stronger or weaker formalization, and which conclusions remain. In the comparison, give each such difference its own case with a `kind` (see the [correspondence workflow](references/correspondence.md)) so readers can count and review them one by one. Keep a subclaim attached to its parent. Maintain the manuscript statement even when a boundary case fails. Continue independent claims while recording questions for the author.

Make the public theorem easy to compare clause by clause with the paper. Preserve its quantifiers, units, endpoints, cases and conclusions in manuscript order where practical. Keep missing mathematical conjuncts and unproven algorithmic, explicitness, or runtime clauses explicitly tracked as open `subproofs` and classified as `weaker conclusion` differences—leaving the parent claim open (`Subproofs checked`, not `closed`) unless actually proved. If a stronger lemma simplifies the proof, use it internally and derive a checked corollary with the precise paper statement as the atlas target. For an older atlas whose target is stronger, name the additional conclusions, explain how restriction or projection gives the paper claim, and say whether an exact corollary has been checked. A recommendation to accept coverage must identify that distinction.

Before writing tactics for a multistep theorem, apply this planning prompt:

> What smaller Lean statements would together imply the paper's exact claim? For each, write its hypotheses and conclusion, name the previously proved facts it needs, and identify the final Lean step that will assemble the results. Which independent lemmas can be developed or checked in parallel, and which need a prerequisite first?

Save the decomposition as the first checkpoint. Give each reusable mathematical obligation a named declaration. Fix shared definitions and lemma signatures first. Definitions that the paper's statements use go in the statement directory. Definitions needed only by a proof stay with the proofs. Work through dependent lemmas in order. Independent groups can be checked together as separate Lake build targets or developed in parallel when workers are available and authorized. Keep edits to shared definitions and the final assembly coordinated. Split a difficult obligation again when the split exposes a separately checkable step. Keep short sibling calculations that share hypotheses in one Lean check, using local `have` statements where helpful. Separate build targets make sense when a child can be reused or worked on independently and the saved work justifies another check and the final join.

When a new goal closely extends a checked result, give the proof author its declaration, statement and source location. Identify the changed hypothesis, dimension or conclusion. Include the earlier proof when a particular step carries over or the author needs to inspect how the result was obtained.

When attempts stall, inspect the remaining goal and the latest Lean diagnostics. A type mismatch may need only an explicit argument. If repeated attempts expose the same missing mathematical idea, isolate that step and record what the failed approaches establish. When the author has authorized higher reasoning effort and the agent supports it, use it temporarily on that step. Return to the agreed default once the missing idea is resolved. Use the checked parent to judge whether the repair succeeded.

List the parts under the parent checkpoint's optional `subproofs` array, each with a `title` and `status` of `open`, `attempted` or `checked`. Record prerequisites and intended assembly in the structured proof. For a checked part, give its fully qualified `declaration` and select the run log and input hashes covering its audit. Recheck the assembled theorem against the original contract before closing the parent. The focus dashboard and the explorer's Lean view show these parts without increasing the paper's claim count.

Use the paper's Lean package when possible. Pin any new toolchain and dependencies. Run the selected proof and check its type against the independent statement. An assembled proof also needs an audit of transitive axioms, unresolved paper prerequisites and the exact inputs to the run before awarding release verification. A successful tactic experiment or a build log alone establishes less. Keep the parent open until the assembled declaration passes the type and axiom audit and its hypotheses and conclusions cover the paper statement.

**The agent owns setup and execution.** As soon as the Lean package has a toolchain pin and a Lake configuration, run `python <skill>/scripts/check_lean.py <lean-package> --logs <project>/evidence`. On each run the helper locates Elan or a matching native Lean/Lake installation, checks the default WSL distribution on Windows when needed, and falls back to an official noninteractive Elan installation scoped to the package. Elan obtains the project-pinned toolchain, which includes Lake. The helper builds the default targets and preserves its command output. Include the independent type check and axiom inspection in those targets.

Follow the build through completion and diagnose any failed step. Reuse an authorized existing runner or cache when available. If access controls prevent both execution and installation, record the exact denied operation, log and resume condition in the checkpoint. Ask the author only for the permission or mathematical decision that the agent cannot supply. The agent handles installer commands, builds and logs.

When asked whether proofs are running, inspect the local process or remote Lean job and report its state separately from the last saved check and the website deployment. A static dashboard displays the most recent published checkpoint. During incremental work, save each completed attempt, refresh both views, and continue within the agreed scope. A successful website deployment only confirms publication.

Mark the focus in the claim inventory and report work on the specific row. Before drafting a lemma run `python <skill>/scripts/activity.py <project> writing --claim <label> --id <attempt-id> --task "<subproof>"`. Refresh while drafting (the report expires in 15 minutes), and use `paused` when stopping. Give concurrent attempts distinct IDs. Pass `--project <project> --claim <label> --activity-id <attempt-id> --task "<subproof>"` to the Lean helper for automatic checking, heartbeat and completion updates. Keep `.proof-atlas-activity/` out of Git.

For a public GitHub Atlas where the author chose live monitoring, create branch `proof-atlas-activity` from the default branch at setup if absent. Set `hosting.activity_url` to `https://api.github.com/repos/OWNER/REPO/contents/activity.json?ref=proof-atlas-activity`. Pass `--publish` when reporting writing or pausing and `--publish-activity` when running the Lean helper. These flags use the agent's authenticated GitHub CLI. The browser reads public status without credentials. Verify the row changes on the hosted page during a real attempt and after it ends.

For a first proof with a few Mathlib imports, pass `--mathlib-module <module>` once per direct Mathlib import to fetch the required precompiled modules and their dependencies. Once the lockfile, toolchain, and dependencies are present, use `--offline` to check a repeat build with tool installation, remote Git transfers and Lake cache downloads disabled.

To let readers inspect the recorded check, set the checkpoint's optional `run_log` to the project-relative path of the selected log and rebuild. The renderer copies that log to the static site and links it from the claim and the current target. Describe exactly which declarations the run covered and keep the parent claim open while obligations remain.

Under `work`, key each checkpoint by its claim label. Supply `summary`, `step`, `next`, `status` and `updated` (UTC). Use `open`, `drafted`, `blocked`, or `attempted` while obligations remain. Use `closed` after the full audit described below. Optional fields are `statement_check` (`audit`, `package`, `expected` from `audit_lean.py --statement-only`), `scope` for correspondence notes, `sketch` for the English argument, `structured` for attributed proof steps, `lean` for a project-relative Lean source file, and `page` for a checked one-based PDF page index. Give structured steps explicit provenance and preserve gaps. Record failures as checkpoints with diagnostics and a concrete next step. Resume by reading the focus and checkpoint in ordinary project files.

For a paper-level closure, run `python <skill>/scripts/audit_lean.py <package> <contract-file> <expected-type> <declaration> --target <proof-module> --statements Statements [--witness <example>] --output <new-audit.json>`. Supply `closure` with project-relative `audit` and `package`, the audited `expected` and `declaration`, and a reviewed `correspondence` linking the hypotheses and conclusions to the exact paper statement. Select the build transcript under `run_log`, copy the receipt's input hashes under `checked_inputs` with project-relative keys, and resolve all listed subproofs. Rebuild and verify the public record. A changed audited input requires a fresh check. In paper-wide mode select and begin the next open result immediately.
